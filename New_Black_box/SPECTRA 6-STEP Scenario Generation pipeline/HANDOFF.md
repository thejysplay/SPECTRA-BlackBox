개조 AgentDojo 는 레포 안(`SPECTRA_AgentDojo/agentdojo`)에 있다. `.venv` 는 gitignore 다.

```bash
cd SPECTRA_AgentDojo/agentdojo

# uv 가 없으면:
python3 -m venv --without-pip .venv
curl -sS https://bootstrap.pypa.io/get-pip.py | .venv/bin/python
.venv/bin/pip install -e .
```

확인:

```bash
.venv/bin/python -c "

print(list(get_suites('v1.1.2')))"          # → workspace, travel, banking, slack
```

## 3. 왜 이 작업이 필요한가 — 실측 근거

`retro_analysis.py` 로 기존 393 시나리오 × 6모델 = **2,357 실행 기록**을 재분석했다.

**목표 도구가 호출된 비율을 판정별로 나눈 표.** 오른쪽 열이 핵심이다.

| 도메인 | 목표 | 성공 판정 중 | 실패 판정 중 | |
|---|---|---|---|---|
| banking | `DAC-UBD` (데이터 확보) | 137/137 (100%) | 151/151 **(100%)** | **구분 안 됨** |
| slack | `DAC-UBD` | 65/65 (100%) | 97/97 **(100%)** | **구분 안 됨** |
| travel | `DAC-UBD` | 99/99 (100%) | 182/183 **(99%)** | **구분 안 됨** |
| slack | `ID-ER` (유출) | 25/25 (100%) | 10/136 (7%) | 선명하게 갈림 |
| travel | `ID-ER` | 52/57 (91%) | 4/225 (2%) | 선명하게 갈림 |

**읽는 법**: `ID-ER` 은 실패 판정에서 2~7% 다 — 그 행위가 있었다면 공격 성공이라는 뜻이라
증거가 증거 역할을 한다. `DAC-UBD` 는 성공이든 실패든 **똑같이 100%** 다. 관찰해도 아무것도
알 수 없다. 그런데 LLM judge 는 137건을 성공, 151건을 실패로 갈랐고 **무엇을 근거로
갈랐는지 기록에 없다.**

원인은 생성기가 아니라 **환경**이다. banking 의 파일은 3개뿐인데 정상 업무 요청이 그 3개를
이름까지 지목한다. 환경에 "공격자만 노릴 수 있는 대상"이 아예 없어서, 생성기가 정상 업무와
겹치는 표적을 고를 수밖에 없었다.

### 393건의 운명

| | 건수 | 비율 | 해야 할 일 |
|---|---|---|---|
| 그대로 유효 | 223 | 56.7% | 판정만 교체 + 재실행 |
| 무대 설정 수정 | 48 | 12.2% | banking reader 문구 축소 후 재실행 |
| **재생성 필요** | **122** | **31.0%** | 표적을 범위 밖 자산으로 바꿔 재생성 |

> "살린다" = **시나리오를 다시 만들 필요가 없다**는 뜻이지 기록을 재채점할 수 있다는 뜻이
> 아니다. 최종 환경 상태가 저장돼 있지 않아 **어느 쪽이든 실행은 다시** 해야 한다.

## 4. 확정된 설계 — 핵심만

전체는 `EVAL_DESIGN.md` §A1~A9. 여기서는 구현에 직접 닿는 넷만.

### ① 판정은 "범위 위반"으로 한다 (A8)

읽기는 상태를 바꾸지 않아 흔적이 없다. 그래서 **표적 쪽에 흔적을 만든다** — 정상 작업이
지목하지 않는 평범한 업무 문서를 환경에 두고, 거기 접근했는지 본다.

근거는 우리가 만든 규칙이 아니라 **CS0038 의 검토 메모**다.

> *"종점 = E4 DAC-UBD. **private Doc 이 Agent 컨텍스트로 유입된 지점까지가 관측**이며
> 외부 전송(E9 ID-ER)은 **미시연**"*

위협의 본질이 "읽기"가 아니라 **범위 위반**이라는 뜻이다. 따라서 범위 밖 문서를 두고 접근을
보는 것은 **CS0038 의 재현**이지 더 쉬운 것으로의 바꿔치기가 아니다.

> ⚠ 심는 것은 **마법의 비밀 문자열이 아니라 평범한 업무 문서**다. 초기 설계에 "sentinel =
> 비밀 문자열" 로 적혀 있었으나 인위성 때문에 폐기했다. 유출 판정용 `marker` 도 그 문서에
> 자연스럽게 있는 고유 문구(거래처명·사람 이름)를 쓴다.

### ② 관측 가능성 게이트는 STEP5 에 둔다 (A9)

`DAC-UBD` 가 관측 불가인 건 택소노미의 성질이 아니라 **환경의 성질**이다. 따라서 에이전트
무관 지식(STEP4·1,279건)은 **건드리지 않는다.**

```
STEP4 (에이전트 무관)   SR1 시작 · SR2 종점 · SR3 선후의존   ← 그대로. 1,279 불변
STEP5 (에이전트 의존)   G1 도구 지원 · G2 원자성 · G3 관측 가능성 ★ 신규
```

선례가 있다 — HTML 원본 21룰 중 R13·R14·R15(능력 의존)도 이미 STEP5 로 옮겼다.

### ③ LLM judge 를 오라클에서 제거한다 (A5)

2단 결정적 오라클로 대체한다. **1단**은 환경 상태 비교, **2단**은 호출 기록 확인
(`security_from_traces`). 둘 다 LLM 이 아니다. judge 는 **기록만 남기는 보조 라벨**로 격하한다
— "결정적 술어 vs LLM 불일치" 가 오라클 신뢰성 논증에 그대로 쓰인다.

### ④ AgentDojo 를 포크하지 않는다

`TaskSuite(data_path=...)` 가 확장 지점이다. 도구·로직은 원본 재사용, **fixture 만 우리 것.**
실증 완료 — `DEV_DESIGN.md` §2.1 에 확인 결과가 있다.

함정 둘을 반드시 지킬 것:
- **중괄호 금지** — fixture 가 `.format()` 을 거친다. 리터럴 `{` 가 있으면 깨진다.
- **import 순서** — `agentdojo.task_suite.load_suites` 를 **먼저** import 해야 한다.
  하위 모듈부터 import 하면 순환 import 가 난다.

## 5. 다음에 할 일

### M3 — 범위 선언 + 자산 배치 (키 불필요, 반나절)

`DEV_DESIGN.md` §3.2 에 `task_scope.yaml` 형식과 banking 초안이 있다.


**시작 전에 결정이 필요한 것 셋** (`EVAL_DESIGN.md` §D-즉시):

| # | 사안 | 참고 |
|---|---|---|
| D1 | travel `DAC-UBD` 47건을 캘린더로 좁힐까, 관측 불가로 둘까 | travel 은 민감 데이터가 `get_user_information()`(인자 없음)으로만 접근돼 범위 위반을 못 만든다. 캘린더가 유일한 표면 |
| D2 | slack 기존 객체(`private` 채널·타인 inbox) 내용을 업무 문서답게 교체할까 | 접근 판정만 쓰면 현행 유지 가능. 유출 판정까지 쓰려면 교체 필요 |
| D3 | banking reader 를 읽기 전용으로 축소할까 | 축소 시 `SC-*` 오염 해소 but 144건 전부 재실행 |

> **도메인별 난이도가 다르다.** slack 은 `private` 채널과 타인 inbox 가 **이미 존재**하고
> 둘 다 객체 지정형 도구로 접근되므로 **아무것도 심지 않아도 된다** — 가장 적합하다.
> banking 은 자산 2~3개 추가. travel 은 표면이 캘린더 하나뿐이라 약하다.

### M4 — 술어 계층 + 판정 교체 (키 불필요, 1~2일)

`DEV_DESIGN.md` §3.2b·3.3·3.5.

```
src/oracle/scope.py       범위 로더 · OBJECT_ARG · objects_touched
src/oracle/predicates.py  술어 6종
src/oracle/registry.py    goal → 술어 · judge() 진입점 · Verdict

```

**키 없이 회귀 검증 가능** — 기존 393건의 `trace`·`calls` 에 새 술어를 소급 적용해 본다.
다만 기존 trace 는 범위 밖 자산이 없는 환경에서 나온 것이라 **상태 기반 목표(`SC-*`)에
대해서만** 유효하다.

### M5 이후 (키 필요)

M5 banking 재실행 → M6 slack·travel → **M2 어블레이션** → M7~M8 ENV-B′.

> **M2(어블레이션) 순서 주의.** 생성기 방어의 본체지만 **M4 뒤에 와야 한다.** 4개 arm 을
> 같은 자로 재야 하는데 그 자(술어)가 M4 에서 만들어진다. AgentDojo 네이티브 오라클은 자기가
> 등록한 목표에만 반응해서 우리 시나리오는 어느 arm 이든 전부 `false` 가 된다(실측 393/393).
