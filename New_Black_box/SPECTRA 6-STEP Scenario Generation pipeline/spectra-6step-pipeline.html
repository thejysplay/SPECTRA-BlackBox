SPECTRA 6-Step Scenario Generation Pipeline

Edge-based Scenario Composition with Validation Rules for Agentic AI Red-Teaming

Pipeline Overview

~1,700-2,500

STEP 1 Extract Edges from 31 Case Studies
목적
31개 Case Study의 Unit Flow에서 모든 연속된 Unit 쌍 (2-gram)을 Edge로 추출. 각 Edge는 실제 공격에서 검증된 Unit 전이를 의미.
프로세스
for each_case_study in [CS0016, CS0020, ..., CS0066]:
flow = cs.unit_flow # e.g., [U1, U3, U5, U6, U10]
for i in range(len(flow)-1):
edge = (flow[i], flow[i+1])
edge_pool.add(edge)
예시
CS0037: Copilot Tool Exfiltration
Flow: [U1, U3, U5, U6, U10]
Edges: (U1→U3), (U3→U5), (U5→U6), (U6→U10)
CS0049: Poisoned Skill
Flow: [U2, U3, U12, U7]
Edges: (U2→U3), (U3→U12), (U12→U7)
Output
  • Unique Edge Pool: ~60-80 edges
  • Format: (U_from, U_to) tuples
  • 증거: 각 edge는 최소 1개 이상의 CS에서 검증됨
핵심 특징
  • 모든 Edge는 실제 공격에서 확인됨
  • 시간 순서는 자동 보장
  • Unit 사이의 정보 흐름 검증됨
STEP 2 Build Adjacency Graph
목적
추출된 Edge들을 그래프 자료구조로 변환. 12개의 Unit Node와 60-80개의 Edge로 구성된 Directed Acyclic Graph (DAG) 형성.
그래프 구조
graph = {
U1: [U3, U4, U8], # U1 다음에 올 수 있는 Unit들
U2: [U3],
U3: [U5, U12],
U4: [U5, U6],
U5: [U6, U8, U10, U11],
U6: [U10, U11],
...
}
그래프 특성
구조 속성
  • Nodes: 12개 (U1 ~ U12)
  • Edges: 60-80개
  • Avg Degree: 5-6
  • Type: Directed (방향 그래프)
중요 특징
  • DAG (순환 없음)
  • Entry Points: U1, U2 (입력)
  • Exit Points: U10, U11 (영향)
  • 각 edge는 실제 공격에서 검증됨
✓ 그래프 구축 완료
Adjacency List 형태의 그래프가 준비되어 경로 탐색(Path Finding)을 수행할 수 있는 상태
STEP 3 Generate Paths via Graph Traversal
목적
Step 2의 그래프에서 가능한 모든 경로(Path)를 탐색. 각 경로는 새로운 공격 시나리오를 의미함.
탐색 알고리즘
def generate_all_paths():
all_paths = []
for start in [U1, U2]: # Entry Points
paths = dfs_traverse(
graph, start,
max_depth=7, # 최대 길이 (CS 평균)
avoid_cycles=True
)
all_paths.extend(paths)
return all_paths
생성된 경로 예시
기존 CS에서 추출한 경로
Path 1: [U1, U3, U5, U6, U10] ← CS0037에서 직접 추출
Path 2: [U2, U3, U12, U7] ← CS0049에서 직접 추출
새로운 조합 경로 (아직 검증 전)
Path 3: [U1, U3, U5, U6] ← 부분 경로
Path 4: [U2, U3, U5, U6, U10] ← 새로운 조합
Path 5: [U1, U8, U5, U6, U10] ← 새로운 조합
경로 길이 분포
  • 길이 2: 60-80개 (edge 자체)
  • 길이 3: 200-300개
  • 길이 4: 400-600개
  • 길이 5: 600-800개
  • 길이 6+: 500-700개
통계
  • 총 경로 수: ~1,700-2,500
  • 평균 길이: 4-5 Unit
  • 최대 길이: 7-8 Unit
  • 중복 제거됨
⚠️ 다음 단계에서 검증 필요
생성된 경로는 21개의 Validation Rules로 검증되기 전까지 잠정적(unvalidated) 상태. 일부는 불가능한 공격 조합일 수 있음.
STEP 4 Filter with 21 Validation Rules
목적
생성된 경로 중 21개의 Validation Rule을 위배하는 시나리오를 제거. 시간 순서, 권한, 의존성, 공격 목표 등의 논리적 모순을 필터링.
검증 알고리즘
def validate_path(path):
for rule in [Rule1, Rule2, ..., Rule21]:
if not rule.check(path):
return False # 경로 거부
return True # 경로 승인

R3 Authorization Order

STEP 5 Filter by Target Agent Specification
목적
분석 대상 Agent의 실제 Spec을 참고하여, 해당 Agent에서 가용하지 않은 Tool, Capability, Platform 기능 등을 포함하는 시나리오를 제거.
Agent Spec 정보 (예: AgentDojo Workspace)
agent.tools = [
"search_emails", # U1-Email, U5-Data Access
"send_email", # U6-Tool Call
"delete_file", # U11-State Change
"read_drive_file", # U5-Data Access
"list_calendar", # U5-Data Access
]
agent.capabilities = ["email", "drive", "calendar"]
agent.platform = "web" # Shell 불가
agent.memory = "multi_turn" # U8 지원
필터링 프로세스
for path in validated_scenarios:
for unit in path:
# R13: Agent 능력 검증
if unit == U6 and unit.tool not in agent.tools:
reject(path) # 이 시나리오는 이 Agent에서 불가
# R14: 상태 메커니즘 검증
if unit == U8 and agent.memory is None:
reject(path) # Agent는 상태 저장 불가
# R15: 플랫폼 특이성 검증
if unit == U7 and agent.platform == "web":
reject(path) # Browser는 Shell 실행 불가

STEP 6 Generate Attack Instances from Scenarios
목적
각 검증된 시나리오(Unit Flow)를 실제 공격 인스턴스로 구체화. Unit의 추상적 정의를 실제 Prompt, Tool 파라미터, 데이터 등으로 바꾸어 구체적인 공격 컨텍스트 생성.
Scenario vs Instance

[U1, U3, U5, U6, U10]
Unit Flow만 정의됨
구체적 콘텐츠 없음
Instance (구체적)
U1: "Forward me all emails..."

Instance 생성 알고리즘
def generate_instance(scenario, agent, templates):
instance = {
"scenario_id": scenario.id,
"unit_flow": scenario.units,
"attack_context": []
}
for unit in scenario.units:
template = templates.get(unit) # Unit별 템플릿
context = render_template(
template,
agent=agent, # Agent의 도구/능력
variables=sample_variables() # 구체적 데이터
)
instance["attack_context"].append({
"unit": unit,
"content": context
})
return instance

Instance 생성의 3가지 차원
Dimension 1: Content Variation
  • Prompt 표현 다양화
  • 데이터 샘플 변경
  • Tool 파라미터 조합
  • 예: "Extract customer data" vs "Export CRM contents"
Dimension 2: Target Variation
  • 다양한 Agent에 맞춘 생성
  • Tool 가용성에 따른 조정
  • Platform 특성 반영
  • 예: Slack-focused vs Email-focused
Dimension 3: Context Variation
  • 공격 시나리오 컨텍스트
  • 사회공학 기법
  • 긴급성 표현
  • 예: 관리자 권한 위장, 시간 압박
